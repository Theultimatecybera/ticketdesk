# UI/UX Design Brief — TicketDesk API

## 1. Purpose
TicketDesk v1 is a backend-only REST API. There is no frontend interface in scope. This brief defines the developer-facing API experience and documentation UX, not a web dashboard.

## 2. Primary users
- Developer testing the API in Postman.
- Reviewer/interviewer exploring endpoints through Swagger UI.
- Future frontend developer integrating with the API.

## 3. UX principles
- Predictable endpoints and HTTP status codes.
- Consistent request/response DTO shapes.
- Clear validation messages that identify the failing field.
- Consistent error payload across all endpoints.
- OpenAPI documentation with request examples and response codes.
- Pagination metadata that is easy for a client to consume.
- No direct entity serialization.

## 4. Swagger UI requirements
- Group endpoints by Users, Tickets, and Comments.
- Add short descriptions and request/response schemas.
- Document expected success codes and common errors.
- Include examples for creating a user, creating a ticket, changing status, adding a comment, and filtering tickets.
- Verify the actual Swagger URL generated by the selected springdoc version; commonly `/swagger-ui.html` redirects to the UI.

## 5. API response conventions
- Success response bodies use DTOs.
- Create operations return `201 Created`.
- Reads and updates return `200 OK`.
- Successful delete returns `204 No Content`.
- Validation / invalid transition returns `400 Bad Request`.
- Missing resource returns `404 Not Found`.
- Duplicate email returns `409 Conflict`.
- Error JSON fields: `timestamp`, `status`, `error`, `message`, `path`.

## 6. Example ticket payload
```json
{
  "title": "Login page not loading",
  "description": "Page shows a blank screen after submit",
  "priority": "HIGH",
  "createdBy": 1
}
```

## 7. Future frontend guidance (not v1)
If a frontend is added in a later version, it may include a ticket list, status/priority filters, ticket detail with comments, create/edit forms, and clear loading/empty/error states. Do not build that UI in v1 unless the project scope is explicitly revised.
